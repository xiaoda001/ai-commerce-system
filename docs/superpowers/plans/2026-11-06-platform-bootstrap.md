# Platform Bootstrap Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a runnable monorepo skeleton and a NestJS readiness endpoint that verifies connections to the developer-managed MySQL, Redis, and Kafka services.

**Architecture:** The workspace contains separate Next.js storefront, React + Ant Design admin SPA, NestJS HTTP API, and NestJS Worker apps. This first slice only establishes bootstrapping, configuration, health probes, and app shells; business modules are implemented in later slice plans. MySQL, Redis, and Kafka stay outside the application workspace and are reached through environment configuration.

**Tech Stack:** TypeScript, npm workspaces, Next.js, React, Ant Design, Vite, NestJS, TypeORM, MySQL, ioredis, KafkaJS, Jest, Vitest.

**Spec:** [2026-11-06-overseas-commerce-system-design.md](../specs/2026-11-06-overseas-commerce-system-design.md)

## Global Constraints

- Customer storefront: Next.js; admin: React + Ant Design SPA; backend: NestJS modular monolith.
- HTTP API and Worker run as separate processes from the same repository and share types through `packages/contracts`.
- MySQL, Redis, and Kafka are separately deployed; connect with environment configuration and never commit credentials.
- MySQL access uses TypeORM migrations; do not use schema auto-synchronization outside isolated tests.
- Health responses must not expose credentials, connection strings, or raw driver errors.
- No AI Agent, real payment, or business feature implementation in this bootstrap slice.
- The repository currently has no `.git` directory; initialize Git before implementation and commit each completed task.
- Proposed workspace manager for this plan: npm workspaces, avoiding an additional monorepo runner. The lockfile pins installed dependencies.

```ts
export type MarketCode = 'US' | 'CN';

export interface ReadinessResponse {
  status: 'ok' | 'error';

    mysql: DependencyStatus;
    redis: DependencyStatus;
    kafka: DependencyStatus;
  };
```

```ts
export interface DatabaseConfig {

  port: number;
  database: string;
  username: string;

export function createTypeOrmOptions(
  config: DatabaseConfig,
): DataSourceOptions;
```

Return TypeORM MySQL connection options with `synchronize: false`, `migrationsRun: false`, and `entities`/`migrations` arrays supplied as empty arrays until feature slices add them. `packages/data-access/src/index.ts` exports the interface and function.

**Interfaces:**
- `GET /health/live` returns `200` while the NestJS process is alive.
- `GET /health/ready` returns `200` and `ReadinessResponse` only when MySQL, Redis, and Kafka are reachable; otherwise it returns `503` with each dependency marked `error` or `ok`.
- `HealthService.checkReadiness(): Promise<ReadinessResponse>` is the only health controller dependency.
- `validate-env.ts` requires `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `REDIS_URL`, and `KAFKA_BROKERS` at startup.
- API listens on `API_PORT` (default `3001`); storefront uses `3000`; admin uses `3002`.
- API scripts: `start:dev`, `build`, `typecheck`, `lint`, and `test`.
